# korean-writing

한국어 글을 **쓸 때** 번역투와 AI 티를 덜 쓰게 하는 스킬이다. 이미 쓴 글을 점검할 때도 같은 규칙을 쓴다(맨 아래 절).
어느 언어로 답할지는 다루지 않는다. 한국어로 쓰기로 정한 뒤의 문체만 본다.

## 이렇게 쓴다

1. **행동의 주어는 사람이나 코드다.** 누가 무엇을 하는지 보이게 능동으로 쓴다.
   "설정이 완료되어야 합니다" 대신 "설정을 마치세요", "에러가 반환된다" 대신 "`parse` 가 에러를 돌려준다".
2. **동사로 쓴다.** "삭제 작업을 수행한다" 대신 "삭제한다". 명사를 쌓지 않는다.
3. **조사로 관계를 말한다.** "~를 통해", "~에 대해", "~에 있어서" 대신 "~로", "~를", "~에서".
4. **한 문장에 한 가지.** 길어지면 끊는다. 연결어미 뒤에 쉼표를 찍고 싶어지면 문장을 나눌 자리다.
5. **결론을 바로 말한다.** "결론적으로", "핵심은 ~이다", "~하는 이유다" 같은 포장 없이 명제부터 쓴다.
6. **글 종류에 맞는 문체로 쓴다.** 독자에게 보이는 기술 문서는 존댓말, 커밋·내부 메모는 해라체가 기본이다.
   아래 표를 따르되, 문서에 이미 일관된 관례가 있으면 그쪽이 먼저다.
7. **그 문서의 관례를 따른다.** 영문 뒤 조사 띄어쓰기, 용어 표기는 주변 글과 저장소의 기존 문서를 보고 맞춘다.

| 글 | 기본 문체 | 예 |
|:--|:--|:--|
| 사이트·README·가이드·API 문서 (외부 독자) | 합쇼체 `~합니다` | "조각 배열을 돌려줍니다." |
| 안내·튜토리얼에서 독자에게 시키는 문장 | `~하세요` | "설정을 마치세요." |
| 커밋 제목·본문 | 해라체 `~한다` | "캐시 경로를 고친다" |
| PR 본문 | 해라체 또는 짧은 명사형 | "경로 계산을 한 곳으로 모은다" |
| 리뷰 답글 (사람에게 하는 말) | 해요체 | "의도한 동작이에요." |
| CLAUDE.md·스펙·설계 메모 (에이전트·본인이 읽음) | 해라체 | "되살리지 말 것." |
| 채팅 설명 | 대화가 쓰던 존댓말 | |

- 한 문서 안에서 문체를 섞지 않는다. 표 칸·코드 주석·목록 조각은 명사형으로 끝내도 된다.
- 기존 문서를 다른 문체로 바꾸는 것은 문체 교정이 아니라 별도 작업이다. 요청이 있을 때만 한다.

자세한 패턴과 before→after 는 `references/patterns.md` 에 있다. 커밋·PR·리뷰 답글처럼 짧은 글은
`references/commit-pr.md` 를 본다.

## 다 쓴 뒤 한 번 훑는다

초안을 내기 전에 아래를 본다. **강한 신호는 한 번만 나와도 고치고, 약한 신호는 여러 번 겹칠 때만 고친다.**

강한 신호:
- 이중 피동: `되어지다`, `~지게 되다`
- `~에 의해` 피동, `가지고 있다`(have 직역), `수행/진행/실시하다`(빈 동사)
- `~를 통해` (수단이면 `~로`)
- AI 관용구: `결론적으로`, `시사하는 바가 크다`, `주목할 만하다`, `~하는 이유다`, `다음과 같다`로 시작하는 열거
- 연결어미 바로 뒤 쉼표가 한 문단에 여럿 (`~하고, ~하며,`)
- 문장마다 붙은 줄표(—) 부연
- 제목·메뉴·frontmatter `title` 이 영어 문서 관습어의 직역(`개념`=Concepts, `레퍼런스`=Reference).
  제목은 본문보다 먼저 본다. 페이지에 실제로 담긴 내용으로 짓는다.

약한 신호 (겹칠 때만):
- `~에 대해`, `~을 위해`, `~고 있다`, 복수 `-들`, `~할 수 있다` 반복
- `~것이다`·`~것.`으로 끝나는 문장, `~것은 ~다` 분열문
- 볼드·괄호 영어 병기가 문단마다 반복

## 고칠 때 지킬 것 (과잉 교정 가드)

- **뜻을 바꾸지 않는다.** 사실·수치·고유명사·코드 토큰·인용은 그대로 둔다.
- **서법을 지킨다.** "~해야 한다"를 "~한다"로, "~일 수 있다"를 "~이다"로 바꾸지 않는다.
- **기술 용어는 원어나 굳은 외래어로 둔다.** API·토큰·머지·리팩터링·이스케이프를 억지로 우리말로 옮기지 않는다.
  반대로 free·emit·run 같은 개발 동사를 일상어 하나로 1:1 옮기면 그것도 직역이다(`놓는다`, `낸다`, `돈다`).
  그 분야에서 실제로 쓰는 말(해제한다, 출력한다, 실행된다)을 고른다.
- **새 상투구를 심지 않는다.** 고치면서 비유·수사·"결국"·"~하는 이유다"를 새로 만들지 않는다.
  쉼표도 고친 뒤에 원문보다 늘면 실패다.
- **용어를 바꿨으면 조사를 다시 본다.** 받침이 바뀌면 조사도 바뀐다(`방언과` → `표기와`). 일괄 치환 뒤 꼭 확인한다.
- **원래 자연스러운 문장은 건드리지 않는다.** 고칠 곳이 없으면 없다고 말한다.

## 이미 쓴 글을 점검할 때

`/korean-writing [경로|PR|글]` 로 불렸거나 "이 글 다듬어줘" 같은 요청이면 아래 순서로 한다.
커밋·PR·리뷰 답글이면 `references/commit-pr.md` 도 읽는다.

1. **대상을 정한다.** 경로면 그 파일, PR 번호·URL 이면 PR 본문, 그 밖이면 받은 글 자체다.
   대상이 없으면 무엇을 점검할지 한 줄로 되묻는다.
2. **그 문서의 관례를 한 줄로 요약한다.** 종결어미, 영문 뒤 조사 띄어쓰기, 용어 표기. 이 관례 안에서 고친다.
   문서 전체의 문체를 바꾸는 것(해라체 → 존댓말 등)은 점검이 아니라 별도 작업이다. 다르면 짚기만 한다.
3. **제목부터 본다.** frontmatter `title`, `#` 제목, 메뉴 라벨이 영어 문서 관습어의 직역인지 확인한다.
4. **본문의 신호를 찾는다.** 강한 신호는 한 번만 나와도, 약한 신호는 겹칠 때만 고친다.
5. **문장 단위 before → after 로 보여 준다.** 강한 신호부터, 각 항목에 무엇을 왜 고쳤는지 한 줄.
   제목·용어를 바꾸면 함께 고쳐야 할 곳(링크 텍스트, 앵커, 내비 라벨, 뒤따르는 조사)도 적는다.
6. **판단이 갈리는 것은 고치지 말고 묻는다.** 관례인지 실수인지 모르는 것, 뜻이 모호해서 고치면 의미가 바뀔 수 있는 것.
7. 고칠 곳이 없으면 없다고 말한다. 사용자가 요청하지 않았으면 파일을 직접 고치지 않는다.
