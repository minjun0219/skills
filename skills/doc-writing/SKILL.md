# doc-writing

문서가 눈에 잘 들어오도록 문서 단위의 구조와 서식을 정하는 스킬이다. 다루는 범위는 정보의 순서, 문단과 목록과 표의 선택, 제목과 굵게의 쓰임이다. 문장 단위의 문체와 번역투는 korean-writing 스킬이 맡는다. 두 스킬이 다 해당하면 이 스킬로 구조를 잡은 뒤 korean-writing으로 문장을 다듬는다.

에이전트 문서가 잘 안 읽히는 데는 이유가 있다. 모델은 선호 학습에서 길고 서식이 많은 답이 좋은 평가를 받아 왔기 때문에 내용과 관계없이 제목, 굵게, 목록을 붙이는 쪽으로 기운다. 그런데 독자는 화면의 글을 다 읽지 않고 훑는다. 요지가 뒤에 묻힌 문서, 굵은 말이 너무 많아 강조가 힘을 잃은 문서, 목록이 항목 사이의 "그래서"와 "다만"을 지운 문서는 눈에 들어오지 않는다. 이 스킬은 이 세 가지를 바로잡는다. 서식을 줄이는 것 자체는 목표가 아니다.

아래 규칙은 모두 기본값이다. 같은 규칙이 어떤 문서에서는 글을 낫게 하고 어떤 문서에서는 나쁘게 만든다. 규칙을 적용하기 전에 "쓰기 전에 정할 것"을 판단하고, "그대로 두는 게 나은 경우"에 해당하면 규칙보다 그 판단을 따른다.

## 상황에 맞는 레퍼런스

이 파일의 규칙은 모든 문서에 쓴다. 특정 상황에만 필요한 내용은 레퍼런스로 나눠 두었으니 해당할 때 읽는다.

| 상황 | 읽을 파일 |
|:--|:--|
| 정해진 유형의 문서를 쓸 때 (작업 결과 보고, 채팅 답변, PR 설명, 설계 문서, ADR, 리서치 요약, README, 회의록) | `references/doc-types.md` |
| 이미 있는 문서를 점검하거나 고쳐 달라는 요청을 받았을 때 | `references/review.md` |
| 고칠지 그대로 둘지 판단이 서지 않을 때 | `references/examples.md` |
| 규칙의 근거를 설명해야 할 때 | `references/sources.md` |

## 쓰기 전에 정할 것

아래 네 가지를 먼저 판단한다. 대개 대화 맥락에서 알 수 있으니 따로 묻지 않는다.

1. 독자: 누가 읽고 이미 무엇을 아는가. 같은 회의에 있던 사람과 문서만 받은 사람은 필요한 맥락이 다르다.
2. 읽는 방식: 답을 찾으러 와서 훑는가, 처음부터 따라 읽으며 배우는가, 단계를 따라 하는가, 필요한 부분만 찾아 들어오는가.
3. 읽은 뒤 할 일: 알기만 하면 되는가, 결정해야 하는가, 실행해야 하는가.
4. 정해진 양식: 사용자가 말한 형식, 팀의 PR 템플릿, 보고서 양식, 저장소의 기존 문서 관례가 있으면 그것이 이 스킬의 규칙보다 먼저다.

## 내용 모양에 맞춰 서식을 고른다

서식은 내용의 모양을 드러낼 때만 읽기를 돕는다. 아래 표에서 내용의 모양을 찾아 서식을 고른다. 한 문서 안에서도 부분마다 모양이 다르면 서식도 달라진다. PR 설명이라면 바꾼 이유는 문단으로 쓰고 바꾼 파일은 목록으로 쓰는 식이다.

| 내용의 모양 | 서식 | 예 |
|:--|:--|:--|
| 인과, 판단, 트레이드오프, 불확실성 | 문단 | 왜 A를 골랐나, 무엇이 위험한가 |
| 서로 독립된 같은 종류의 항목 | 불릿 목록 | 바꾼 파일, 설정값, 남은 할 일 |
| 순서가 있는 단계 | 번호 목록 | 설치 절차, 재현 방법 |
| 여러 대상을 기준 여러 개로 비교 | 표 | 라이브러리 비교, 옵션별 차이 |
| 긴 문서에서 독자가 골라 읽을 단위 | 제목 | README의 설치, 설정, API |
| 코드, 명령, 경로, 식별자 | 코드 블록, 백틱 | `useAuth`, `pnpm build` |

목록과 문단 사이에서 헷갈리면 항목 사이에 "그래서", "왜냐하면", "다만"을 넣어 본다. 자연스럽게 들어가면 관계가 있는 내용이니 문단으로 쓴다. 넣을 자리가 없으면 병렬 항목이니 목록으로 둔다. 판단의 근거가 되는 짧은 항목 두세 개는 문단 안에서 쉼표로 나열해도 된다. 독자가 하나씩 대조해 볼 조건이나 할 일이면 목록으로 둔다. 표는 비교 기준이 둘 이상일 때 쓴다. 기준이 하나면 목록이나 문장으로 충분하다.

굵게는 독자가 놓치면 문제가 생기는 내용에만 쓴다. 경고, 되돌릴 수 없는 작업, 독자가 내려야 할 결정이 그렇다. 한 문단에 굵은 말이 여럿이면 시선이 그 말들만 찍고 지나가서 문장의 논리가 읽히지 않는다. 이모지와 장식용 수평선도 내용을 더하지 않으니 쓰지 않는다. 다만 팀 문서가 이모지를 관례로 쓰면 따른다.

라벨 뒤에 콜론과 설명을 붙인 목록(`원인: 설명`)은 독자가 범주별로 찾아 읽는 요약에 맞다. 회고 요약의 원인, 영향, 조치처럼 라벨이 독자가 찾는 범주이고 설명이 완결된 문장이면 라벨 사이에 인과가 있어도 목록으로 둔다. 위의 "그래서" 시험은 라벨 없이 조각으로 끝나는 목록에 쓴다. 반대로 "코드 분석", "원인 파악"처럼 작업 순서를 라벨로 붙였거나 `**원인 파악:** 훅 분석`처럼 설명에 정보가 없으면 독자가 찾는 범주가 아니니 문단으로 풀어 쓴다.

보이는 곳도 고려한다. 채팅 앱이나 터미널처럼 마크다운을 일부만 렌더링하거나 폭이 좁은 곳에서는 열이 많은 표와 깊은 제목 구조가 깨지기 쉽다. 그런 곳에서는 짧은 목록이나 문단을 쓴다.

## 정보 순서

요지를 맨 앞에 둔다. 요지는 질문에 대한 답, 작업의 결과, 문서의 결론처럼 독자가 가장 먼저 알아야 할 내용이다. 첫 문장이나 첫 문단에 요지를 두고 그 뒤에 근거와 세부를 둔다. 첫머리를 질문의 재진술, 문서 구성 예고, 배경 설명에 쓰면 훑어 읽는 독자는 요지에 닿기 전에 떠난다. 끝에 본문을 되풀이하는 요약이나 맺음 인사는 붙이지 않는다. 길이는 독자가 할 일에 필요한 만큼이면 된다.

이 순서가 맞지 않는 경우가 있다.

- 결론이 아직 없으면 지어내지 않는다. 아직 정하지 못했다는 사실과 무엇이 정해져야 하는지를 앞에 둔다. 브레인스토밍, 조사 중간 메모, 방향이 없는 결정 요청 문서가 여기에 해당한다.
- 개념을 먼저 알아야 결론을 이해할 수 있는 학습 문서나 튜토리얼은 맥락을 먼저 둔다. 이때도 첫 문단에서 이 문서를 읽으면 무엇을 할 수 있게 되는지 밝힌다.
- 긴 문서는 요지 다음에 구성 안내를 한두 문장 둘 수 있다. 구성 안내로 문서를 시작하지는 않는다.

요지를 앞에 둘 때는 확신의 정도도 같은 자리에 쓴다. 확인하지 못한 내용을 앞에서 단정하면 독자는 처음부터 잘못된 방향으로 읽는다. 확인하지 못한 것 가운데 요지의 확신을 바꾸는 것(실기기에서 확인하지 못한 성능 개선 등)은 요지와 같은 문단에 쓰고, 요지와 별개인 후속 확인 사항은 뒤로 보낸다.

## 그대로 두는 게 나은 경우

이 스킬을 읽고 나면 모든 목록을 문단으로 바꾸고 모든 제목에 요지를 담고 싶어진다. 아래 경우에는 원래 형태가 더 잘 읽히니 바꾸지 않는다.

- 독자가 맥락을 공유하는 짧은 기록. 회의록, 스탠드업, 진행 상황 공유, 체크리스트는 개조식이 더 빠르다. 문장으로 풀면 길어지기만 한다.
- 병렬 사실의 목록. 바꾼 파일, 환경 변수, 의존성, 남은 작업은 목록이 맞고 항목을 명사로 끝내도 된다.
- 기준 여러 개로 비교하는 내용. 표가 문단보다 빨리 읽힌다.
- 필요한 부분만 찾아 들어오는 참조 문서. README, API 문서, 런북, 설정 가이드에는 "설치", "설정", "문제 해결" 같은 예측 가능한 범주 이름이 제목으로 낫다. 요지를 담은 제목은 보고서나 설계 문서처럼 요지를 훑는 문서에 쓴다.
- 이미 잘 읽히는 문서. 고칠 곳이 없으면 없다고 말한다.

## 한국어 문서에서

한국어 보고서의 개조식('-함', '-임', 명사로 끝나는 항목)은 짧게 압축하기에는 좋지만 주어, 서술어, 항목 사이의 관계를 지운다. "전환"이라고만 쓰면 전환했다는 건지 전환할 예정이라는 건지 알 수 없다. 그래서 판단, 인과, 계획, 불확실성을 담은 항목은 주어와 서술어가 있는 문장으로 쓴다. 파일 이름, 설정값, 수치 같은 단순한 병렬 사실은 명사로 끝내도 된다. 회의록처럼 독자가 맥락을 공유하는 짧은 기록은 계획과 결정도 개조식으로 둔다.

한 목록 안에서는 항목을 끝맺는 방식을 맞춘다. 명사로 끝나는 항목과 문장으로 끝나는 항목이 섞이면 독자가 항목마다 성격을 다시 따져야 한다. 단순 사실과 판단이 한 목록에 섞이면 모두 문장으로 맞춘다. 문체, 번역투, 조사, 띄어쓰기는 korean-writing 스킬을 따른다.

## 다 쓴 뒤 점검

초안을 내기 전에 아래를 본다.

1. 제목과 각 문단의 첫 문장만 이어 읽는다(skim test). 요지와 독자가 할 일이 전달되지 않으면 첫 문장을 고친다.
2. 첫 두 문장 안에 요지가 있는지 본다. 결론이 없는 문서라면 그 사실이 앞에 있는지 본다.
3. 서식마다 이유를 댈 수 있는지 본다. 목록은 항목이 병렬일 때, 표는 비교 기준이 둘 이상일 때, 제목은 독자가 골라 읽을 이유가 있을 때, 굵게는 놓치면 안 되는 내용에만 쓴다.
4. 대화에서만 쓰던 약칭, 파일 이름, 변수 이름이 설명 없이 나오는지 본다. 문서만 받은 독자는 그 맥락을 모른다.

아래는 다시 들여다볼 신호다. 틀렸다는 판정이 아니므로 이유가 있으면 그대로 둔다.

- 한 화면에 다 들어가는 답변에 제목이 있다.
- 한 문단에 굵은 말이 둘 이상이다.
- 목록이 세 단계 이상 중첩된다.
- 항목이 하나뿐인 목록이나 비교 기준이 하나뿐인 표가 있다.
- 제목이나 목록 항목 앞에 이모지가 붙어 있다.
- 끝에 본문을 되풀이하는 요약, 맺음 인사, 의례적인 추가 도움 제안이 있다.
- 작업 순서만 있고 결과가 없다.

## 고칠 때 지킬 것

- 사실을 더해도 되는지는 그 사실을 직접 확인했는지로 정한다. 이번 작업에서 확인한 사실이면 빈 라벨 뒤에 숨기지 말고 쓴다. 글만 받아 고칠 때는 원문에 없는 사실, 결론, 추천, 수치를 더하지 않는다. 서식을 바꿔 나아진 글과 내용이 늘어 나아 보이는 글은 다르다. 같은 뜻을 질문에 맞게 바꿔 말하는 것은 괜찮지만, 원문이 정하지 않은 판단을 넣으면 내용을 더한 것이다. 결론이 필요한데 없으면 지어내지 말고 짚는다.
- 목록을 문단으로 바꾸는 일은 항목 사이에 관계가 있을 때만 한다.
- 신호의 개수를 맞추려고 고치지 않는다. 굵게를 두 개에서 하나로 줄이는 식의 수정은 글을 낫게 하지 않는다.
- 단정의 정도를 올리지 않는다. 요지를 앞으로 옮기면서 "-일 수 있다"를 "-이다"로 바꾸지 않는다.
- 고친 결과가 원문보다 길어졌으면 다시 본다. 관계를 문장으로 살리면 조금 길어질 수 있지만, 같은 말을 되풀이해서 길어졌다면 잘못 고친 것이다.
- 팀 양식과 문서의 기존 관례는 바꾸지 않는다. 다르게 하고 싶으면 짚기만 한다.
