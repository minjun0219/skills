# 예시

고치는 경우, 그대로 두는 경우, 상황에 따라 다른 경우를 하나씩 보인다.

## 고친다: 작업 결과 보고

Before:

```markdown
## 📋 작업 요약
요청하신 로그인 버그 수정 작업을 완료했습니다! 아래에 상세 내용을 정리했습니다.
### 🔍 분석 과정
- **원인 파악:** `useAuth` 훅 분석
- **코드 수정:** 토큰 갱신 로직 개선
- **테스트:** 관련 테스트 추가
### ✅ 결론
로그인 버그가 성공적으로 해결되었습니다.
```

After:

```markdown
토큰이 만료된 순간 요청이 동시에 여러 개 나가면 갱신이 중복 호출돼 로그아웃되던 문제를 고쳤습니다. `useAuth`에서 진행 중인 갱신이 있으면 뒤따르는 요청이 그 갱신을 기다리게 했습니다.

- 확인 필요: 리프레시 토큰까지 만료된 경우는 로컬에서 재현하지 못했습니다. 스테이징에서 확인해 주세요.
- 테스트: 동시 요청 3건 시나리오를 `auth.test.ts`에 추가했습니다.
```

원인과 해결은 "그래서"로 이어지는 관계라서 문단으로 썼다. 확인 필요와 테스트는 서로 독립된 항목이라 라벨 목록으로 남겼다. After에 쓴 사실은 작업한 에이전트가 이미 확인한 내용이다. Before는 그 사실을 빈 라벨 뒤에 숨겼다. 글만 받아 점검하는 경우라면 이 After처럼 쓸 수 없으니 빈 라벨을 짚고 빠진 사실을 작성자에게 묻는다.

## 그대로 둔다: 병렬 사실 목록

원문:

```markdown
바꾼 파일
- `src/auth/useAuth.ts`: 갱신 요청을 하나로 묶음
- `src/auth/auth.test.ts`: 동시 요청 테스트 추가
- `src/api/client.ts`: 401 응답 처리 위치 이동
```

잘못 고친 예:

```markdown
이번 작업에서는 `useAuth.ts`에서 갱신 요청을 하나로 묶었고, 이에 맞춰 `auth.test.ts`에 동시 요청 테스트를 추가했으며, `client.ts`에서는 401 응답 처리 위치를 옮겼습니다.
```

항목 사이에 인과가 없는데 한 문장으로 이어 붙여서 파일을 찾기만 어려워졌다. 원문이 맞다.

## 상황에 따라 다르다: 판단이 담긴 개조식

원문:

```markdown
상태 관리 라이브러리 교체 검토
- 번들 크기 증가
- 마이그레이션 비용 존재
- 장기적 유지보수성 개선
```

결정을 요청하는 문서라면 이렇게 고친다.

```markdown
상태 관리 라이브러리를 교체할지 정해야 합니다. 교체하면 장기적으로 유지보수가 쉬워지지만 번들 크기가 늘고 마이그레이션 비용이 듭니다.
```

원문에 추천이 없으니 고친 글에도 추천을 넣지 않았다. 판단에 필요한 정보(번들 증가량, 마이그레이션 기간)가 비어 있으면 그 점을 짚는다. 같은 목록이 회의 참석자끼리 보는 메모라면 원문이 더 낫다.
