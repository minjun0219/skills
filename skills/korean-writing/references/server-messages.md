# 서버·API 메시지

서버가 만드는 문구다. 먼저 **누가 읽는지**를 정한다. 읽는 사람에 따라 언어·문체·내용이 다르다.
값이 끼워 들어가는 문구는 `message-variables.md`도 읽는다.

| 읽는 사람 | 자리 | 언어·문체 |
|:--|:--|:--|
| 기계 (클라이언트 분기) | 오류 코드, `type`, `reason` | 영어 식별자. 번역하지 않고 바꾸지 않는다 |
| 개발자 (API 소비자, 운영자) | 응답의 `message`·`detail`, 로그 | 저장소 관례. 한국어로 쓰면 합쇼체 완전한 문장 |
| 최종 사용자 | 화면에 뜨는 문구 | 제품 UI 문체. `web-ui.md`를 따른다 |

## 구조

1. **서버는 코드와 파라미터를 보내고, 사용자 문구는 클라이언트가 만든다.** Google AIP-193은 `Status.message`를
   개발자용 디버그 메시지로 정의하고, 사용자에게 보일 문구는 `LocalizedMessage`로 따로 보낸다. 분기는 바뀌지 않는
   `reason`(`UPPER_SNAKE_CASE`)으로 한다. [AIP-193]
2. **RFC 9457 Problem Details를 쓰면** `title`은 같은 문제면 매번 같은 문구로 둔다(현지화만 예외). `detail`은
   클라이언트가 문제를 고치는 데 도움이 되는 말만 담고 디버그 정보는 넣지 않는다. 클라이언트는 `detail`을 파싱하지 않는다.
   파싱할 값(`limit`, `retryAfter`)은 확장 멤버로 보낸다. [RFC 9457]
3. **서버가 사용자 문구를 직접 보내야 하면** `Accept-Language`로 언어를 고르고, 문구 전체를 카탈로그 키 하나로 만든다.
   조사·숫자는 `message-variables.md` 대로.
4. **로그에는 문구가 바뀌어도 그대로인 식별자를 남긴다.** 로그 문구를 번역해도 검색·집계는 코드로 한다. [Google]

```json
{
  "type": "https://example.com/problems/quota-exceeded",
  "title": "Quota exceeded",
  "detail": "Monthly export quota of 100 reached.",
  "limit": 100
}
```

클라이언트는 `type`과 `limit`으로 `이번 달 내보내기 한도 100건을 다 썼어요. 다음 달 1일에 다시 쓸 수 있어요.`를 만든다.

## 문구

개발자가 읽는 `message`·`detail`·로그도 사람이 읽는 글이다. CLI 오류와 같은 원칙을 쓴다(`cli-tui.md`의 표준 구문).

| 기계 | before | after |
|:--|:--|:--|
| 판단 | `Internal Server Error`를 그대로 화면에 표시 | 화면: `일시적인 문제로 저장하지 못했어요. 잠시 뒤 다시 시도해 주세요.` / 로그: `ORDER_SAVE_FAILED` + 원인 |
| 판단 | `잘못된 요청입니다.` | `start_date는 end_date보다 앞이어야 합니다. 받은 값: 2026-10-20, 2026-10-16` |
| 검출 | `요청 처리 중 에러가 발생되었습니다` | `요청을 처리하는 동안 오류가 발생했습니다.` |
| 검출 | `유저에 의해 취소됨` | `사용자가 취소했습니다.` |
| 판단 | `{"message": "이메일을 입력해 주세요"}`로만 분기 | `{"code": "EMAIL_REQUIRED", "field": "email"}` + 클라이언트 문구 |

- 사용자 화면에 서버의 원문 오류(스택, SQL, 예외 이름)를 보이지 않는다. 문의용으로 요청 ID 정도만 보인다.
- 사과(`죄송합니다`)는 서비스 쪽 장애에만 쓰고 사용자 입력 오류에는 쓰지 않는다.
- 같은 오류는 어느 엔드포인트에서 나든 같은 코드·같은 문구를 쓴다.
