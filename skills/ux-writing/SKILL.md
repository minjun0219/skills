# ux-writing

제품이 사용자에게 보여 주는 한국어 문구를 쓰는 스킬이다. 웹·앱 화면, CLI·TUI 출력, 서버·API 메시지를 다룬다.
이미 쓴 문구나 i18n 카탈로그를 점검할 때도 같은 규칙을 쓴다(맨 아래 절).
문서·README·커밋·PR 본문처럼 읽는 글은 korean-writing 스킬이 맡는다.

## 어디에 뜨는 문구인지 보고 레퍼런스를 고른다

아래 규칙은 모든 제품 문구에 쓴다. 문구가 뜨는 자리에 따라 해당 레퍼런스를 **먼저** 읽는다. 둘 이상에 걸치면 모두 읽는다.

| 뜨는 자리 | 읽을 파일 |
|:--|:--|
| 웹·앱 화면 (버튼, 라벨, 제목, 토스트, 다이얼로그, 폼 오류, 빈 상태, 플레이스홀더, 푸시, `aria-label`) | `references/web-ui.md` |
| 터미널 (CLI 진행·성공·오류, 프롬프트, 도움말, TUI) | `references/cli-tui.md` |
| 서버·API (오류 응답의 `message`·`detail`, 로그, 서버가 보내는 사용자 문구) | `references/server-messages.md` |
| 값이 끼워 들어가는 문구 (`{name}`·`%s`·i18n 카탈로그 `ko.json`·`.po`) | `references/message-variables.md` (위 셋과 함께) |

레퍼런스 표의 `기계` 열은 스크립트로 검사하거나 고칠 수 있는지를 표시한다. 뜻은 `message-variables.md` 머리말에 있다.

## 먼저 보이스를 정한다

문체는 문구마다 고르지 않고 **제품 단위로** 정한다. 제품에 이미 문구가 있으면 그 체를 따른다.
없으면 처음 한 번 정해서 저장소 문서(가이드·`AGENTS.md`)에 적는다.

| 제품·출력 | 기본 문체 | 예 |
|:--|:--|:--|
| 일반 소비자 앱·서비스 | 해요체 | `저장했어요.` `다시 입력해 주세요.` |
| 업무용 도구·개발 도구·공공 서비스 | 합쇼체 + 지시는 `-세요` | `저장했습니다.` `다시 입력하세요.` |
| CLI 출력 | 합쇼체 + 지시는 `-세요` | `'mytool login'을 먼저 실행하세요.` |
| 개발자가 읽는 서버 `message`·`detail`·로그 | 저장소 관례. 한국어로 쓰면 합쇼체 완전한 문장 | `start_date는 end_date보다 앞이어야 합니다.` |
| 약관·법률 고지 | 보이스와 별개로 합쇼체 (`-십시오` 포함) | |

- 한 화면, 한 도구 안에서 체를 섞지 않는다.
- 기존 문구의 체를 바꾸는 일은 별도 작업이다. 요청이 있을 때만 한다.
- 근거와 예외(해요체에서 과한 경어 빼기 등)는 `web-ui.md`·`cli-tui.md`의 문체 절에 있다.

## 이렇게 쓴다

1. **사람이 한 일은 능동으로 쓴다.** `비밀번호가 변경되었습니다` 대신 `비밀번호를 바꿨어요`.
   수동형은 서비스 종료·기간 만료처럼 주어(서비스·기간)를 강조할 때만 쓴다.
2. **명사를 쌓지 않고 동사로 푼다.** `본인 인증 진행 후 서비스 이용 가능` 대신 `본인 인증을 하면 바로 쓸 수 있어요`.
   `~를 통해`·`~에 대해` 대신 조사로 관계를 말한다.
3. **요소마다 꼴을 맞춘다.** 버튼·라벨·메뉴는 명사나 `~하기`로 쓰고 마침표를 찍지 않는다.
   본문·토스트·오류는 완결된 문장으로 쓰고 마침표를 찍는다. 요소별 표는 `web-ui.md`에 있다.
4. **오류는 고칠 방법까지 쓴다.** 무엇을 못 했는지, 왜인지, 어떻게 하면 되는지 순서로 쓴다.
   사용자를 탓하지 않고, 사과는 서비스 쪽 잘못에만 한다. `실패`는 명사로만 쓰고 동사 자리에서는 `~하지 못했습니다`로 쓴다.
5. **할 수 있는 것을 먼저 말한다.** `없어요`·`안 돼요` 대신 `~하면 할 수 있어요`. 정책상 막힌 기능은 부정형을 쓰되 이유를 함께 쓴다.
6. **문장 하나는 키 하나다.** 조각을 이어 붙이지 않는다. 변수 뒤 조사는 코드로 계산하거나, 변수 뒤에 명사를 두거나, 병기한다.
   자세한 순서는 `message-variables.md`에 있다.
7. **영문·코드 뒤 조사는 붙여 쓴다.** 한글 맞춤법 제41항 "조사는 그 앞말에 붙여 쓴다"는 앞말이 영문이나 코드여도 같다.
   `API를`, `'main'으로`, `start_date는`. 조사는 영어를 읽는 소리의 받침으로 고른다.
8. **같은 개념은 같은 말로 쓴다.** `오류`와 `에러`, `닫기`와 `취소`처럼 갈리는 말은 제품에서 하나로 정하고 섞지 않는다.
9. **기계가 읽는 것은 번역하지 않는다.** 오류 코드·`reason`·`--json` 출력·로그 키는 영어 식별자 그대로 둔다.
10. **확인한 만큼만 말한다.** `성공적으로`나 느낌표로 들뜬 느낌을 내지 않는다.
    할 능력이 없는 것은 `~할 수 없습니다`, 시도했다가 안 된 것은 `~하지 못했습니다`로 나눈다.

## 다 쓴 뒤 한 번 훑는다

내기 전에 아래를 본다. **강한 신호는 한 번만 나와도 고치고, 약한 신호는 여러 번 겹칠 때만 고친다.**

강한 신호:
- 사람이 한 일의 수동·이중 피동: `변경되었습니다`, `업데이트되어졌습니다`, `에러가 발생되었습니다`
- 동사 자리의 `실패`: `복사를 실패하였습니다`, `찾는데 실패`
- 해요체 제품의 과한 경어: `사용하실 수 없으십니다`, `~께`, `계시다`
- 들뜬 완료 문구: `성공적으로 저장되었습니다!`, 무엇이 됐는지 없이 `완료!`만
- 원인과 해결이 없는 오류: `오류가 발생했습니다.`만, `잘못된 입력입니다`, 여러 경우를 하나로 덮는 `필수 항목입니다`
- 사용자 입력 오류에 붙은 `죄송합니다`
- 버튼·라벨의 마침표, 본문·토스트에 빠진 마침표
- 지시나 설명이 들어간 플레이스홀더
- 이어 붙인 문장 조각(`t('delete') + name + t('done')`), 변수 뒤 고정 조사(`{name}를`), 뒤바뀐 병기(`{name}를(을)`)
- 숫자와 단위 사이 띄어쓰기(`{n} 개`), 숫자 변수 뒤에 빠진 단위
- 글자 수를 맞추려고 뺀 띄어쓰기, `되어요`, `..`로 쓴 줄임표(`...`는 프로젝트 관례를 따른다)
- 영문·코드 뒤에 띄어 쓴 조사(`API 를`)
- 목적지가 드러나지 않는 링크 텍스트(`여기`)

약한 신호 (겹칠 때만):
- `없어요`·`안 돼요`로 끝나는 안내가 이어짐. 할 수 있는 것을 먼저 말할 수 있는지 본다
- `보러가기`처럼 무엇을 보는지 빠진 버튼
- 해요체 제품에서 `~시겠어요?`·`~시나요?`가 문구마다 반복. 사용자만 아는 사실을 묻는 설문 문장이면 그대로 둔다

## 고칠 때 지킬 것 (과잉 교정 가드)

- **뜻을 바꾸지 않는다.** 수치·고유명사·코드 토큰·자리 표시자(`{name}`, `%s`, `%1$s`)·HTML 태그는 그대로 둔다.
- **키와 기계가 읽는 값은 건드리지 않는다.** i18n 키 이름, 오류 코드, `--json` 출력은 코드가 읽는 값이다.
- **들어갈 자리를 지킨다.** 고친 문구가 원래 자리(버튼, 탭, 푸시)에 들어가는지 본다. 길면 띄어쓰기를 빼지 말고 말을 줄인다.
- **보이스를 지킨다.** 합쇼체 제품이면 합쇼체 안에서 고친다.
- **영어판이 있으면 뜻만 맞춘다.** 한국어 문구를 영어 문장에 한 줄씩 맞추지 않는다. 영어의 `one`/`other` 복수 분기도 옮기지 않는다.
- **용어를 바꿨으면 조사를 다시 본다.** 받침이 바뀌면 조사도 바뀐다. 일괄 치환 뒤 꼭 확인한다.
- **원래 자연스러운 문구는 건드리지 않는다.** 고칠 곳이 없으면 없다고 말한다.

## 이미 쓴 문구를 점검할 때

`/ux-writing [경로|PR|문구]`로 불렸거나 "이 에러 메시지 봐줘", "ko.json 검토해줘" 같은 요청이면 아래 순서로 한다.

1. **대상을 정한다.** 경로면 그 파일(컴포넌트, `ko.json`, `.po`), PR 번호·URL이면 PR diff에 든 문구, 그 밖이면 받은 문구 자체다.
   대상이 없으면 무엇을 점검할지 한 줄로 되묻는다.
2. **문구마다 어디에 뜨는지 가린다.** 카탈로그라면 키 이름과 그 키를 쓰는 코드를 보고 버튼·오류·토스트 같은 요소를 정한다.
   가린 자리에 맞는 레퍼런스를 읽는다. 코드를 봐도 알 수 없으면 묻는다.
3. **제품의 관례를 한 줄로 요약한다.** 보이스, `오류`/`에러`, `닫기`/`취소`, 줄임표. 이 관례 안에서 고친다.
   관례가 문구마다 갈리면 짚기만 하고, 하나로 정하는 일은 사용자에게 묻는다.
4. **신호를 찾는다.** 강한 신호는 한 번만 나와도, 약한 신호는 겹칠 때만 고친다.
5. **키나 위치 단위로 before → after를 보여 준다.** 강한 신호부터, 각 항목에 무엇을 왜 고쳤는지 한 줄.
   문구를 바꾸면 함께 바꿔야 할 곳(같은 문구를 쓰는 다른 키, 테스트의 기대 문자열)도 적는다.
6. **판단이 갈리는 것은 고치지 말고 묻는다.** 관례인지 실수인지 모르는 것, 화면을 봐야 정할 수 있는 것.
7. 고칠 곳이 없으면 없다고 말한다. 사용자가 요청하지 않았으면 파일을 직접 고치지 않는다.
